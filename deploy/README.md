# Отчет по практическому занятию №18: Репетиция деплоя (FoodHub)

## 1. Архитектура проекта

В качестве единой точки входа в приложение используется веб-сервер **nginx**, настроенный как обратный прокси по протоколу HTTPS. Только у него опубликованы сетевые порты на локальный интерфейс (`127.0.0.1:80` и `127.0.0.1:443`).

* Все запросы по пути `/` перенаправляются на контейнер фронтенда (`frontend`).
* Запросы по пути `/api/` перенаправляются на контейнер бэкенда (`backend`) с передачей заголовков `X-Forwarded-*` и добавлением `X-Robots-Tag: noindex, nofollow`.
* Внутренние сервисы изолированы во внутренней сети Docker Compose и недоступны извне напрямую.

```text
[ Браузер ] ---> HTTPS (443) ---> [ nginx (foodhub.localhost) ]
                                    |---> /     ---> [ frontend (React + Vite, порт 80) ]
                                    |---> /api/ ---> [ backend (ASP.NET Core, порт 8080) ]
```

## 2. Таблица сервисов

| Сервис | Технология | Внутренний порт | Продакшен-сервер |
| :--- | :--- | :--- | :--- |
| `nginx` | Nginx (`nginx:1.27-alpine`) | `80`, `443` | Nginx (обратный прокси и SSL) |
| `frontend` | React + Vite (TypeScript) | `80` | Nginx (раздача собранной статики) |
| `backend` | C# / ASP.NET Core | `8080` | Kestrel (`dotnet FoodHubApi.dll`) |

## 3. Переменные окружения и секреты

В репозитории и Docker-образах не хранятся конфиденциальные данные. Используются следующие переменные:

* `ASPNETCORE_ENVIRONMENT` — режим запуска бэкенда (`Production`).
* `VITE_API_URL` — аргумент этапа сборки фронтенда, задающий относительный базовый путь для запросов к API (`/api`).
* Локальные TLS-сертификаты (`foodhub.localhost.pem` и `foodhub.localhost-key.pem`) подключаются к контейнеру `nginx` при запуске через `volumes` и исключены из Git через `.gitignore` (`deploy/certs/`).

## 4. Команды запуска и остановки проекта

Все команды выполняются из директории `deploy/`:

* **Сборка образов и запуск всех сервисов в фоновом режиме:**
  ```bash
  docker compose up --build -d
  ```
* **Проверка статуса контейнеров:**
  ```bash
  docker compose ps
  ```
* **Просмотр журналов работы сервисов:**
  ```bash
  docker compose logs -f
  ```
* **Остановка и удаление контейнеров:**
  ```bash
  docker compose down
  ```

## 6. Возникшие ошибки и способы их устранения

1. **Конфликт адресов фронтенда и бэкенда при работе за обратным прокси:** при разработке фронтенд обращался к бэкенду напрямую по `https://localhost:7023/api`. **Решение:** вынесен адрес API в переменную `VITE_API_URL` (значение по умолчанию сохранено для локальной разработки), при сборке в Docker передается `/api`, а `nginx` проксирует `/api/` на `http://backend:8080`.
2. **Корректная обработка заголовков прокси и индексации API:** при работе за `nginx` бэкенду необходимо понимать исходный протокол и хост запроса, а ответы API не должны попадать в поисковую выдачу. **Решение:** в `Program.cs` добавлен `UseForwardedHeaders` и middleware для заголовка `X-Robots-Tag: noindex, nofollow`, продублированный в конфигурации `nginx.conf`.

## 7. Что нужно изменить для публикации проекта на реальном сервере

1. **Аренда сервера и соблюдение 152-ФЗ:** арендовать VPS/VDS у российского хостинг-провайдера (чтобы персональные данные пользователей хранились и обрабатывались на серверах в РФ) и установить Docker.
2. **Доменное имя и DNS:** зарегистрировать реальное доменное имя у регистратора и настроить A-запись в DNS, указывающую на публичный IP-адрес сервера.
3. **Публичный SSL-сертификат:** заменить локальные сертификаты `mkcert` на доверенный сертификат от публичного центра сертификации (например, Let's Encrypt с автоматическим продлением через Certbot).
4. **Сетевая доступность и CI/CD:** убрать привязку к `127.0.0.1` в портах `nginx` (`80:80` и `443:443`), перенести секреты в защищенное окружение сервера и настроить автоматическую доставку образов (CD) на сервер.
